上个月新来的技术员接手排料程序，我让他自己去把算余料那段找出来。他把单元文件往下翻了三屏，指着一行说，是不是这个。

那行函数名就叫 `算余料`。

按道理这不算什么本事。可要是满屏 `CalcRemain`、`IsSheetFitable`，他得先在脑子里翻一遍再判断对不对，翻错一次就往错的方向看半天。技术部没人是科班出身，车间转过来的居多，英文水平大概就够看图纸上的标注。

## 中文名省下来的是翻译那一秒

我们这套东西从头到尾中文命名。函数名 `算余料`、`判断板能不能放下`，变量名 `当前余料`、`排版明细`，数据库里的库名表名也是中文，连字段都是。

一开始只是图省事：脑子里想的是"这个人要算余料"，手就打出来了，不用停下来想英文该怎么拼。写得久了才发现省的不是敲键盘那几下，是省掉了"写的时候翻译一次、读的时候再翻译一次"。

真正的收益出现在两种时候。

一种是半夜。车间打电话说某个单子排不出来，你得在黑漆漆的电脑前十分钟内找到问题。这时候脑子里只剩"是不是余料判错了"，手能直接搜到 `算余料` 那个函数。要是叫 `CalcRemain`，你得先在搜索框里试两三种拼法。

另一种是交接。这套程序现在不是我一个人在改，新人接手时最怕的不是逻辑复杂，是"我不知道这东西在哪"。中文名相当于给代码贴了一层标签，标签写的就是他在车间里天天说的词。

## 撞墙的地方，都不是给人看的

不过中文命名也不是哪儿都能用。这几年撞过几次，每次都不是语法问题，都是"机器过手"的地方。

最典型的一次是视频。我们用程序调 ffprobe 读一个 mp4 的时长，文件名是中文，报错说 `Illegal byte sequence`（非法的字节序列）。文件明明在那儿，路径也是对的。原因是 Windows 下命令行程序拿到的路径是 GBK 编码，而程序内部按 UTF-8 解，中文名到那一层就变成乱码了，它按乱码去找文件，当然找不到。这个不是 ffprobe 的毛病，任何吃外部路径的原生程序都可能碰上。

另一处是网址。博客文章的文件名、URL 里那一段（就是 slug），一定用英文。我最早有篇文章懒得起，让程序拿中文标题去生成网址，结果那篇点进去就是 404。博主的后台不认识这个中文路径，页面根本没生成出来。

还有 JSON 的键、配置文件的项名。这些是给程序读的，不是给人读的。写中文进去也不会立刻报错，等到哪天换了个工具去读，它在解析那一步就挂了，而且报错指向的行号跟你写的东西毫无关系。

## 分界线

| 场景 | 用什么 | 理由 |
|------|--------|------|
| Delphi 函数名、变量名、注释 | 中文 | 写的人读的人都是车间出身的，中文省一次翻译 |
| 数据库库名、表名、字段名 | 中文可以，但库和表必须 utf8mb4 | MySQL 从 5.x 起就支持中文标识符，前提是字符集对 |
| 传给外部程序的路径、命令行参数 | 英文，或者先转码 | Windows 下原生程序吃 GBK，程序内部是 UTF-8，中间会错一层 |
| 网址、文件名、slug | 英文或拼音 | 中文网址能编码，但工具链上任何一环都可能不认 |
| JSON 的键、配置项名 | 英文 | 机器读的，出问题时报错也指不到点上 |
| 对外接口的字段 | 英文或拼音 | 将来对接别人的系统，这一层动不了 |

## 做法

真要落地，不用开会定规范，就一句：**人看的地方用中文，机器过手的地方用英文**。

判断也很简单，闭上眼睛问一句，这个东西会不会被程序当成一个名字去识别。会，就用英文。不会，就是给人读的，敞开了用中文。

还有个笨办法很好用：给外部程序传中文路径之前，先把它复制到一个纯英文的临时目录里再传。多写两行代码，比在那儿查 `Illegal byte sequence` 查到怀疑人生划算。

新人现在也这么写。前两天我看他新加的一个函数，叫 `判断要不要拆板`。挺好，这名字车间听得懂。
