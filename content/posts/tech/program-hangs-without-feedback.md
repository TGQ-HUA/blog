## 引子

前天下午，技术部的小姑娘在导图库模板，四百多个。

点了"开始导出"，鼠标变成沙漏，窗口白掉，标题栏后面挂上"（无响应）"。

她等了两分钟，认定死机了，任务管理器结束任务。重新打开，又点了一遍，怕没点上，又点了一遍。等我过去看，导出目录里一堆半截文件，外加三份一模一样的。

她不是没耐心。是程序从头到尾没告诉她一个字：在跑、跑到第几个、还有多久。

## 一个人又收银又炒菜

Windows 程序有一条主线程。按钮点击、窗口重绘、"你要不要关闭窗口"这些消息，全在这条线程上排一条队，一个一个处理。

你在按钮事件里写个 `for i := 1 to 428 do`，这条线程就被占住了。它没空去重画界面，也没空理会你点的"关闭"。用户看到的就是一个白框。Windows 那边大概五秒钟收不到消息，就把"（无响应）"给你挂上——这个"（无响应）"是系统判定的，不是程序自己报的，所以它往往是用户最先看到的"故障信息"。

车间里有个差不多的说法：一个人又收银又炒菜，客人一多，两头都顾不上。主线程就是那个收银的。你让他去后厨炒四百个菜，前台就没人了。

## 我早期用的那招，挤牙膏

先承认，这个我写过：

```delphi
for i := 1 to 总数 do
begin
  处理一个;
  进度条.Position := i;
  Application.ProcessMessages;   // 挤出一点时间给界面
end;
```

界面会动了，进度条一格一格走。当时觉得挺聪明。

它带来的问题比解决的还多。

第一，能重复点。`ProcessMessages` 在挤时间的同时，把按钮点击消息也处理了。用户在循环跑到一半的时候再点一次"开始导出"，第二个循环就起来了，两个循环同时改同一批文件。前面那三份一模一样的文件，就是这么来的。

第二，能关窗。用户不耐烦，直接把窗口关了，循环还在后台跑，跑完去访问已经释放的控件，报访问违例。这类崩溃最难查，因为报错的地方和出事的地方隔了几百行。

第三，越跑越慢。频繁把时间让给界面，整体速度明显掉。

`ProcessMessages` 不是不能用，是不能拿来跑业务。它只适合"我确定这一下最多两百毫秒"的情况，比如刷新一个状态标签。

## 现在的写法：活给后台，话给前台

原则很简单：重活交给后台线程，后台不碰控件，只往前台递消息。

```delphi
// 报进度：序号按值传进去，每次调用一份独立的副本
procedure 报进度(序号, 总数: Integer);
begin
  TThread.Queue(nil,
    procedure
    begin
      进度条.Position := 序号;
      状态标签.Caption := Format('正在导出 %d / %d', [序号, 总数]);
    end);
end;

// 按钮事件里
TTask.Run(
  procedure
  var
    i: Integer;
    失败数: Integer;
    失败清单: TStringList;
  begin
    失败清单 := TStringList.Create;
    try
      for i := 1 to 总数 do
      begin
        if 已取消 then Break;              // 用户点了取消，随时能停
        try
          处理一个(i);
        except
          on E: Exception do
          begin
            失败清单.Add(Format('第 %d 个：%s', [i, E.Message]));
            Inc(失败数);
          end;
        end;
        报进度(i, 总数);
      end;
      报结果(失败数, 失败清单);              // 完成或中断，都给一句明确的话
    finally
      失败清单.Free;
    end;
  end);
```

这里有个坑我得单说，因为我自己踩过：进度别在循环里直接 `TThread.Queue` 抓 `i`。`i` 是循环外声明的同一个变量，等界面真正执行那条排队消息的时候，`i` 早就跑到末尾了，你会看到进度条从头到尾只显示最后那个数。所以要用一个过程把序号按值传进去，每次调用一份独立副本。

三条底线：后台线程不碰控件，跨线程直接改控件会随机崩，根本没法复现；一个文件出错不能拖垮整批，记下来最后一起报；一定有取消标志，哪怕只判断一次。

## 网络那一步，先判死

导出还连着数据库和共享盘。网络一断，数据库连接默认会在那儿慢慢等，等到它自己超时才报错。这几十秒里，用户看到的还是白框，和死机没区别。

我们的做法是先探一下再连：

```delphi
// 连之前先问一句，问不通就别往下走
if not 探通服务器(服务器地址, 端口, 3000) then
begin
  ShowMessage('服务器连不上，先检查网络或问下网管。');
  Exit;
end;
```

超时设三五秒，连不上就直接说话，不装死。

我宁可它三秒之内告诉我"不通"，也不想它憋三分钟，最后甩一句"操作失败"。后者用户什么也学不到，只能再点一次。

## 老做法和新做法，摆一块看

| | 以前 | 现在 |
|---|---|---|
| 界面 | 白屏，标题挂"（无响应）" | 进度条 + "第 137 / 428 个" |
| 用户能做的 | 只能猜，然后强杀 | 能取消，点了就停 |
| 中途关窗 | 崩，报访问违例 | 先问一句，后台收尾 |
| 单个文件出错 | 整批白干 | 记下来，其余照跑，最后汇总 |
| 网络断了 | 憋到超时 | 三秒内说"连不上" |
| 代码量 | 少 | 多一层线程，值这个钱 |

## 买来的软件，也一样

去年我们试过几个现成的排版算量工具，功能其实够用。真正让人放下的不是功能，是操作完了没反馈：点一下，鼠标转圈，转多久不知道；关掉再点，出两份。

工厂里的人对电脑的耐心，是按秒算的。他手上还有别的活，机器不动他就上手，这是职业习惯，不是态度问题。所以自研工具的第一条，不是功能多，是随时让人知道它在干嘛。

这一点上，我们和那些大厂软件没什么区别。区别在于，大厂的软件我们改不了，自己写的能改。

## 说回那批模板

改完之后她重新导了一次，四百多个，坐在那儿看进度条走。走到 428，弹出来一句："完成。3 个文件名重复，已跳过。"

她把那句话截图发到群里，说这回心里有底了。

以前出了岔子，她第一句话是"电脑又不行了"。现在她会说"它说有三个重复的"。
