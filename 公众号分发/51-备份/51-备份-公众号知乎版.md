# 上个月电脑蓝屏，报价数据差点全没了——风管厂数据库备份，从手工拷贝到自动定时

上个月有天早上，技术部小姑娘小周跑过来喊：唐工，系统进不去了。

我过去一看，装数据库那台电脑蓝屏重启了，MySQL 服务起不来，报错说数据文件损坏。折腾了半小时，确认坏了三个表文件，其中就有材料单价表。

当时心里真是一沉。报价、基础数据、出错登记，全厂的数据都在这台机器上。要是真没了，一个月都补不回来。

还好，出事前一周刚把自动备份配上。数据导出来，一点没丢。

## 一、以前怎么"备份"的：靠人想起来

前两年我们的备份方式，就是谁想起来了，手动拷一份数据库文件夹到 U 盘。坑全踩过一遍：

**第一坑，拷的时候库还在写。** MySQL 正在运行的时候直接复制数据文件夹，拷出来的文件是坏的，还原的时候报错，等于白拷。

**第二坑，想起来才拷。** 报价旺季一忙，三周没人碰 U 盘。真出事那天，最新的数据恰恰是没拷的那部分。

**第三坑，备份和原数据放一个盘。** 备份放 D 盘，数据也在 D 盘。硬盘一挂，备份跟着一起完蛋。这种备份，出了事才知道等于没有。

## 二、现在的方案：四件事，全是基础操作

**1. mysqldump 每天凌晨自动导出一份**

用的就是 MySQL 自带的 mysqldump：

```bat
mysqldump -uroot -p密码 --single-transaction 风管数据 > D:\备份\风管数据_20260807.sql
```

加 `--single-transaction` 是为了导出的时候数据保持一致，不出现"导了一半，正在写的表没导全"的情况。文件名带日期，哪天的数据一眼就看得出来。

**2. Windows 计划任务定时跑**

任务计划程序里建一个任务，每天凌晨 2 点跑上面那条命令。凌晨厂里没人用系统，导出不干扰白天的活。建好之后测一次，确认能正常生成文件。

**3. 保留 30 天，到期的自动删**

```bat
forfiles /P D:\备份 /M *.sql /D -30 /C "cmd /c del @path"
```

只留最近 30 天。风管厂的业务，一个月内的数据最值钱，再老的基本用不上，真需要查老账还有纸质记录和 Excel 留底。

**4. 备份必须放另一块盘**

数据库在 C 盘，备份就放 D 盘；只有一块盘，就加一块硬盘，或者拷到另一台电脑。同盘备份等于没备份，这条是拿教训换的。

## 三、光备份不够，还得验证

备份文件躺在那，不代表恢复得了。我们吃过亏：有一次手动拷的备份，真到恢复那天才发现文件是坏的，白高兴一场。

现在两条规矩：

**每周五抽查一个备份**，恢复到测试库，看能不能正常打开、数据全不全。

**每个月做一次完整恢复演练**，把最近的备份恢复到测试机器，跑一遍系统。半小时的事，换来真出事那天不慌。

## 四、备份检查清单

| 动作 | 怎么做 | 频率 |
|------|--------|------|
| 自动导出 | mysqldump + 计划任务，凌晨跑 | 每天 1 次 |
| 保留周期 | forfiles 自动清理 | 30 天 |
| 备份位置 | 另一块盘，或另一台电脑 | 必须异地 |
| 抽查恢复 | 备份恢复到测试库，看数据全不全 | 每周五 |
| 完整演练 | 备份恢复到测试机器，跑一遍系统 | 每月 1 次 |
| 日志检查 | 早上看一眼昨天的备份文件在不在 | 每天 |

最后那条最容易被忽略。定时任务跑没跑、文件生成没有，得有人看。我们现在的做法是每天早上到厂，小周先看一眼昨天的备份文件在不在，在，就放心干活。

上个月那台电脑，后来换了硬盘，数据一条没丢。但那天早上站在蓝屏前头的十几分钟，我到现在还记得。

备份这事，丢一次，就够你记一辈子。趁没丢，赶紧把定时任务建上。
