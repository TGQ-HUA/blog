# 一卷钢板三个单价，翻了三份表才敢填数

## 风管厂把基础数据搬进了 MySQL

上周二，技术部小姑娘小周拿着报价单来找我，一脸为难："唐工，这单要报 0.8 镀锌板的价格，我翻了三份表——一份写着 48，一份写着 52，还有一份是 50.5。我该填哪个？"

我接过一看，三份表来源都不一样：一份是去年报价留底，一份是采购随口说的，还有一份是同事自己电脑里存的"最新版"。三份表都是真的，也都过期了。

这种场景不稀奇。风管厂干久了都懂：最乱的从来不是图纸，是那些基础数据。

## 一、基础数据有多乱

报价、算量、做损耗核算，天天要用的就是这几样：材质、厚度、单价、折算系数。

这东西看着简单，散起来要命。采购调价了，改一份 Excel；车间说损耗不对，又改一份；等到真要报价，谁都不知道手头这份是不是最新的。更麻烦的是折算系数——S弯、弯头、三通，展开面积怎么折算，每个老师傅心里都有一本账，账和账还不一样。

以前我们试过用共享文件夹统一，结果一个"最终版"后面跟了五个"最终版(1)""最终版(2)"。改的人以为改了大家就都看见了，其实看见的只有他自己。

## 二、为什么搬进 MySQL

我自学 Delphi 那会儿就听人讲数据库，当时觉得那是大公司 ERP 才用的东西，咱一个小厂用不上。后来发现想岔了。

数据库解决的不光是"存储"，关键是**一份数据，多人同时读**。材料单价放进去，采购改一次，所有人下次打开看到的就是同一个数。不存在"我这是旧版"。

我们系统里现在就是这么用的（MySQL 部署在局域网一台服务器上）：

| 基础数据 | 放哪 | 谁维护 | 谁在用 |
|---------|------|--------|--------|
| 材质/厚度/单价 | MySQL 材料编辑模块 | 指定专人 | 报价、算量、出错登记 |
| 折算系数 | MySQL 系数折算模块 | 技术主管 | 绩效核算、损耗计算 |
| 出错损耗折算 | MySQL 自动算 | 系统按材质×平方×单价 | 出错登记 |

出错登记那个最有意思：以前出了错，损耗多少钱靠人估，估多估少全凭感情。现在登记的时候选材质、填平方，单价从库里直接带出来，系统自动折算。数字摆在那，谁都没话说。

## 三、不是换工具，是立规矩

把 Excel 换成 MySQL，表面是技术问题，根子上是习惯问题。

Excel 的好处是随便谁都会改，双击就能编辑。数据库的"不好"，在于它逼着你定规矩——谁有权限改、数据格式什么样、单位统一不统一。很多厂子卡在这一步：嫌麻烦，又退回 Excel 了。

但我们试过之后觉得，这规矩值得立。单价含税不含税、按吨算还是按平方算，这些以前靠嘴交代的事，现在建表的时候就得明确下来，反倒把隐患提前排掉了。

## 四、行业现状

说句实在的，风管厂这类小厂，用不起也不需要用那些动辄几十万的 ERP。但 MySQL 是免费的，装一台普通电脑当服务器就够用。

问题是大多数厂子卡在"觉得没必要"上。人脑存得下 200 个单价，存不下"哪个是最新"这个事实。等出错、扯皮、返工，成本早就超过那点折腾劲了。

我们这套从 Excel 到 MySQL 的迁移，没什么高深技术，就是 Delphi 连数据库，写几个增删改查。难的是下决心把"人管数据"改成"数据管数据"。这一步迈出去，后面顺得很。

## 实操上注意这几条

有同行问过我，从 Excel 往数据库搬，先搬什么？我的经验是：

**1. 先搬单价和系数，别急着搬全部**
单价、系数是最容易被改乱、最影响报价的，先动这两块。订单、图纸那些先留在原处，等跑顺了再逐步迁移。

**2. 单位必须定死**
含税不含税、吨还是平方、毫米还是米，建表前写清楚。单位不统一，数据库照样会打架。

**3. 一个人负责改，其他人只读**
数据维护权收拢到一个人手里，其他人只有查看权限。改数据的人越少，版本越不容易乱。

**4. 每天备份，出了事能回滚**
MySQL 的备份不复杂，写个定时任务每天导出一份。别等数据库崩了才想起来备份，那时候哭都来不及。

**5. 出错记录自动带出单价**
把出错登记和单价表关联起来，损耗成本自动算。这一步能少吵很多架。

我说行。你看，数据库这东西，用顺手了，人自己会往里加东西。
